# قائمة الأمان قبل إطلاق التطبيق

قائمة طلبتها المالكة تُراجع قبل كل إطلاق للتطبيق أو تحديث كبير للموقع. النتيجة أدناه من فحص 2026-10-09 بعد دمج فرع التطبيق مع الموقع. تدقيق جلسة الموقع المفصّل في `docs/security/AUDIT.md` و`docs/security/PRELAUNCH-CHECKLIST.md`.

| # | البند | الحالة | الدليل / الملاحظة |
|---|---|---|---|
| 1 | لا مفاتيح API في الواجهة أو التطبيق | ✓ | لا مفاتيح سرية في `src` أو `mobile`. الموجود فقط `NEXT_PUBLIC_VAPID_PUBLIC_KEY` (عام بطبيعته) ورابط الموقع. |
| 2 | تغيير أي مفتاح لمس GitHub | ✓ لا شيء | فحص كامل سجل git: لا مفاتيح حقيقية، فقط أمثلة نصية. ملفات `.env` غير مرفوعة (فقط `.env.example`). أي مفتاح أُرسل في محادثة أو بريد يُغيَّر احتياطاً. |
| 3 | RLS على كل جدول | ✓ | كل الجداول عليها RLS. جداول الدخول (`user`، `session`، `account`، `verification`، `rateLimit`) و`schema_migrations` أُضيفت في `036_auth_tables_rls.sql` من جلسة الموقع: مكتبة الدخول تعمل بدون هوية، وداخل طلب المتدرب يرى صفّه فقط، ولا يتغير الدور من اتصال التطبيق. |
| 4 | التحقق من الدخول في كل مسار API من الخادم | ✓ | كل المسارات تتحقق من الجلسة، عدا العامة عمداً: `health`، `mobile/v1/content`، `mobile/v1/programs` (بيانات عامة)، و`payments/webhook` (معطّل، يرجع 501). جسر عمليات التطبيق قائمة مغلقة وكل عملية تتحقق بنفسها. |
| 5 | حد للمحاولات في الدخول والتسجيل وما يكلّف | ✓ | رمز الدخول: 5 إرسالات/10 دقائق لكل IP، و8 لنفس البريد بالساعة، وسقف عام 300 بالساعة؛ الدخول 10 محاولات/10 دقائق، و5 محاولات لكل رمز. الطلبات 6/ساعة لكل مستخدم و20 لكل IP، الإيصالات 10/ساعة، بحث الأكل وحذف الحساب لها حدود. |
| 6 | التحقق من كل مدخل في الخادم | ✓ | مخططات zod في العمليات، وقيود قاعدة البيانات، ودوال SECURITY DEFINER تتحقق من الملكية والحالة. |
| 7 | لا SQL مبني بالنصوص | ✓ | كل القيم معاملات (`$1`). أسماء الجداول المتغيرة من قوائم ثابتة فقط، وقيم `batch` عبر `lit()`/`litList()`. |
| 8 | CORS على الدومين فقط | ✓ | لا ترويسات CORS، فالمتصفح يمنع المواقع الأخرى. Better Auth يتحقق من المصدر (`trustedOrigins`)، وعمليات الخادم تتحقق من Origin. |
| 9 | كوكيز httpOnly وsecure وsameSite | ✓ | إعدادات Better Auth: httpOnly، sameSite=lax، وsecure في الإنتاج (`useSecureCookies`). |
| 10 | تشفير كلمات المرور | ✓ لا ينطبق | لا كلمات مرور: الدخول برمز على البريد، والرموز تُخزَّن مشفّرة (hashed). |
| 11 | لا ثقة في user ID من العميل | ✓ | الهوية دائماً من الجلسة. الموضعان الوحيدان اللذان يقرآن `user_id` من النموذج عمليات للمدربة على عضو، وقاعدة البيانات تتحقق أنها المدربة. |
| 12 | إخفاء تفاصيل الأخطاء في الإنتاج | ✓ | Next يخفيها في الإنتاج. أخطاء قاعدة البيانات لا تُعرض إلا رسائلنا العربية (P0001)، وغيرها رسالة عامة. |
| 13 | فحص الحزم عن ثغرات معروفة | ✓ بعد الإصلاح | الموقع: كانت 3 عالية (Next.js منها تسميم الكاش بين المستخدمين، sharp، source-map-js) ← حُدّث Next إلى 16.4.0 وsharp إلى 0.35.5، والنتيجة 0. ⚠️ الموقع الحي على النسخة القديمة حتى الدمج. التطبيق: ثغرات في أدوات بناء Expo (لا تُشحن مع التطبيق) و`decode-uri-component` داخل expo-router (أثر منخفض، يُصلح مع تحديث Expo). |
| 14 | ترويسات الأمان | ✓ | CSP، HSTS، X-Frame-Options=DENY، nosniff، Referrer-Policy، Permissions-Policy في `next.config.ts`. |
| 15 | حدود صرف على الخدمات المدفوعة | ✓ في الكود / ⚠️ على المالكة | حدود الكود أعلاه (البريد، البحث، الرفع). المطلوب من المالكة: تنبيهات صرف في Netlify وNeon ومزوّد البريد. |
| 16 | البحث عن كل ثغرة | مستمر | يُعاد هذا الفحص قبل كل إطلاق، مع مراجعة أمنية للتغييرات الجديدة. |
